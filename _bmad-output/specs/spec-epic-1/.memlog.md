- (direction) input is INTENT.md (Epic 1 done-when / must-not-change / out-of-scope), read alongside mcp/triage_server.py and seed/*.csv for grounding; input is rich so extracted directly, no elicitation
- (capability) CAP-1 triage decision schema: every decision is a JSON object with category (billing|bug|access|performance|how-to), priority (P1-P4), route (billing-team|bug-team|access-team|performance-team|how-to-team) and a one-sentence rationale; anything else is rejected with a clear error
- (capability) CAP-2 seed loader: uv run python load_seed.py loads seed/tickets.csv and seed/customers.csv into local SQLite app.db as tables tickets and customers with the same columns as the CSVs; running it twice gives the same database (idempotent)
- (constraint) Python 3.12 or newer, managed with uv
- (constraint) files in seed/ are read-only
- (constraint) no network calls and no API keys in this epic
- (constraint) mcp/triage_server.py already reads app.db (get_ticket, get_customer_history); tables tickets(ticket_id,customer_id,created_at,text) and customers(customer_id,name,plan,open_tickets) and those column names must keep working
- (non-goal) the agent, the MCP tools, evals and any user interface are out of scope for this epic
- (assumption) category-to-route pairing (e.g. billing -> billing-team) is not stated in INTENT.md; the schema treats route as an independent field and does not enforce the pairing (mismatch policy left to TRIAGE_POLICY.md / Epic 2)
- (question) should the schema reject a decision whose route does not match its category (e.g. category billing, route bug-team), or only validate each field's allowed values?
- (question) what does the loader do with column types (all TEXT vs INTEGER for open_tickets)? INTENT.md only requires the same columns as the CSVs
- (assumption) 'rejected with a clear error' means a validation exception naming the offending field and its allowed values; the exact exception type and module name are left to implementation (Epic 2 imports the schema and loader)
- (assumption) 'same database' on a second run means identical table contents and schema, not byte-identical file
